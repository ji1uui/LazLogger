# MuninnLog 開発プロセス計画

状態: 提案
何を作るか・どの順で作るかは [00_DEVELOPMENT_POLICY.md](00_DEVELOPMENT_POLICY.md)（ロードマップ M0〜M5、品質ゲート）を正本とする。
本書は **どう作るか**（作業の単位、ブランチと PR、CI、テスト、外部コンポーネントとの連携、文書と意思決定、リリース）を定める。

## 1. 前提

| 項目 | 前提 |
|---|---|
| 体制 | 開発者 1 名（プロダクトオーナー兼レビュアー）と、AI コーディングエージェント（Claude Code、Codex など）。人数が増えたら第 13 節を見直す |
| リポジトリ | `ji1uui/LazLogger` の `MuninnLog/` 配下。公開リポジトリ |
| 外部コンポーネント | HamlibComponent（別リポジトリ、Rev.6.0）、HuginnEngine（別途開発） |
| ツールチェーン | Free Pascal 3.2.2、Lazarus 4.4（[ADR 0001](adr/0001-toolchain.md) で固定） |

## 2. 過去の教訓とプロセスへの反映

`Lazarus/` の開発で起きたこと（[01_CURRENT_STATE_REVIEW.md](01_CURRENT_STATE_REVIEW.md)）を、仕組みで防ぐ。

| 起きたこと | 原因 | 防ぐ仕組み |
|---|---|---|
| コンフリクトの両側が残ったままマージされ、master がビルド不能になった | マージ後にビルド・テストをしていない | CI 合格をマージの必須条件にする（ブランチ保護）。コンフリクト解決後は必ずローカルでビルドとテストを実行する |
| CI が赤いままマージが続いた | CI が任意だった | 同上。赤い CI のままのマージを禁止する |
| 実装より先に文書が「完了」と書いた | 完了の定義が文書基準だった | 完了の定義（第 4 節）を「動く機能＋CI 合格」にする。状況報告には CI 実行のリンクを必須とする |
| 基盤や試作が先行し、利用者に見える機能がなかった | 縦割りでなく層ごとに作った | 各イテレーションで利用者が触れる機能を一本通す |
| 1 本 1,500 行の手書きテストランナー | テストの仕組みを決めずに始めた | M0 でテストの仕組みを先に決める |

## 3. 開発サイクル

```text
マイルストーン（M0〜M5）
 └─ イテレーション（2 週間を目安）
      └─ タスク（1 タスク = 1 PR = 1 つの論点）
```

### イテレーションの流れ

| 時点 | やること | 成果物 |
|---|---|---|
| 開始時 | マイルストーンの残りから、2 週間で終わる量のタスクを選ぶ。各タスクの完了条件を書く | GitHub Milestone と Issue |
| 期間中 | タスクごとにブランチを切り、PR を作り、CI 合格とレビュー後にマージする | PR |
| 終了時 | Windows / macOS の実機でデモを行う（ビルド成果物を実際に起動する） | デモの記録（動画またはスクリーンショット、確認した項目） |
| 終了時 | 振り返り：予定と実績の差、詰まった点、プロセスの改善 | 振り返りメモ（Issue のコメント） |

マイルストーンの終わりには、第 9 節の品質ゲートを満たしたうえで、利用者向けの配布版（アルファ以降）を作る。

## 4. 作業の単位

### 着手の条件（Definition of Ready）

- Issue に目的、範囲、完了条件、関連する設計文書の節が書かれている
- 依存するタスクが終わっている、または模擬実装で代替できる
- 1 つの PR に収まる大きさである（目安として、差分が数百行以内で、レビューが 1 回で済む）

### 完了の条件（Definition of Done）

- CI（Windows / macOS / Linux）がすべて合格している
- 変更した部分の単体テストがある。バグ修正なら、そのバグを再現するテストがある
- 利用者に見える変更なら、実機で動作を確認している（確認した OS を PR に書く）
- 設計に影響する変更なら、同じ PR で設計文書を更新している
- 未実施の検証は「未検証」と明記している

## 5. ブランチと PR

| 規則 | 内容 |
|---|---|
| 方式 | master を常に動く状態に保つ。作業ブランチは短命（数日以内）にする |
| ブランチ名 | `feature/<Issue番号>-<短い説明>`、`fix/…`、`docs/…`。AI エージェントは各ツールの命名規則に従ってよく、タスクごとに分けず同じブランチを使い続けてもよい |
| master への変更 | 開発者の変更も含めて、すべて PR を経由する（開発者の判断、2026-10-19） |
| PR の範囲 | 1 つの論点に絞る。整形・改名・無関係なリファクタリングを混ぜない |
| PR の本文 | 目的、変更内容、検証結果（実行したコマンドと結果、CI のリンク）、未検証の項目、関連 Issue |
| マージ方式 | squash マージ。master の履歴を「1 PR = 1 コミット」に保ち、問題が起きたら PR 単位で戻せるようにする |
| コンフリクト | 作業ブランチに master を取り込み、解決後に**ローカルでビルドとテストを実行してから** push する |
| レビュー | 人のレビュー（開発者本人）を必須とする。AI のレビュー（Codex Review など）は補助として使う |

### リポジトリ設定（開発者が GitHub の設定で行う）

- master のブランチ保護：PR 経由のみ、MuninnLog の CI 合格を必須、レビュー 1 件以上を必須
- squash マージのみ許可
- PR テンプレート（`.github/pull_request_template.md`）を追加する（M0 のタスク）

## 6. AI エージェントとの協働ルール

AI エージェントが作業の大部分を担う前提で、次を守る。

1. **同じファイルを複数のエージェントに並行して触らせない。** 作業ブランチはタスクごとに分けなくてよい（開発者の判断、2026-10-19）。同じブランチを使い続ける場合は、PR がマージされたら master から作り直す。
2. **指示は Issue に書く。** 目的、範囲、完了条件、読むべき設計文書の節を、[タスク指示のひな形](#付録-aタスク指示のひな形)に沿って書く。
3. **検証の証跡を必須にする。** エージェントは実行したビルド・テストのコマンドと結果を PR に貼る。CI のリンクがない「完了」は受け付けない。
4. **設計の決定は人が行う。** 決定事項（D 番号）や未決事項（Q 番号）の変更は、エージェントが提案し、開発者が承認してから反映する。
5. **リポジトリにエージェント向けの指示書を置く。** `MuninnLog/CLAUDE.md`（Claude Code 用）と `MuninnLog/AGENTS.md`（その他のエージェント用）に、ビルド・テストの方法、依存の向き、禁止事項を書く（M0 のタスク）。
6. **公開してよいかを確認する。** 未公開の資料や資格情報を、公開リポジトリにコミットしない。

## 7. CI

| ワークフロー | 起動条件 | 内容 |
|---|---|---|
| `muninnlog-ci.yml` | `MuninnLog/**` を変更する push と PR | Windows / macOS / Linux で、中核ライブラリと CLI のビルド、単体テスト、結合テスト、ゴールデンテスト。GUI のビルドは GUI のコードができてから加える（ADR 0001） |
| `muninnlog-nightly.yml` | 毎日 1 回と手動 | 3 OS の GUI と CLI のビルド成果物を保存する。性能測定を実行し、基準値と比較する（未作成） |
| `muninnlog-release.yml` | タグの push | 配布物の作成、署名（Windows）、署名と公証（macOS）。M1 の終わりまでに整える |

- **ツールチェーンの固定：** FPC と Lazarus の版を固定し、CI と開発環境で同じ版を使う。
- **インストール方法：** 3 OS で安定して入る方法を M0 で検証する。前回の `Lazarus/` の CI では、Windows の Chocolatey 経由の取得が失敗している。
- **CI での無線機テスト：**
  - HamlibComponent と Hamlib ライブラリを CI に入れる。
  - Hamlib のダミー機種（model 1）を相手に、無線機アダプターのテストを実行する。

## 8. テスト戦略

| 層 | 対象 | 方法 | 実行場所 |
|---|---|---|---|
| 単体 | ドメイン、規約エンジン、入出力、プロファイル | FPCUnit（M0 で採用を確定）。LCL・OS・通信に依存しない | CI（毎回） |
| ゴールデン | 規約ごとの得点・重複・マルチ、ADIF / Cabrillo / JARL 電子ログの往復変換 | `muninn-cli` に固定データを入力し、期待する出力と照合する。固定データは `MuninnLog/tests/golden/` に置き、個人情報を含めない | CI（毎回） |
| 結合 | SQLite のマイグレーション、Yata Logic の読み込み（署名不正・破損を含む）、HamlibComponent（ダミー機種）、HuginnEngine（模擬エンジン） | 実際の部品を組み合わせる | CI（毎回） |
| 障害 | 強制終了、ディスク満杯、エンジンの異常終了、無線機の切断、PTT の解除 | 故障を注入するテスト | CI（毎回）と夜間 |
| 性能 | 入力から画面反映まで、10 万件の検索・重複チェック・再計算、起動時間 | 測定プログラム。基準値との差で退行を検出する | 夜間 |
| 実機 | 実際の無線機（代表機種）、実際の音声デバイス、実際のコンテスト運用 | 手動のチェックリスト | マイルストーンの終わり |
| UX | キーボード操作、ダーク / ライト、高 DPI、日本語・英語、スクリーンリーダー | 手動のチェックリスト | マイルストーンの終わり |

## 9. 外部コンポーネントとの連携

### HamlibComponent

| 項目 | 方針 |
|---|---|
| 取り込み方 | 版を固定して取り込む（git submodule、または版番号付きでソースを同梱）。M0 で方式を決める |
| 更新 | HamlibComponent の新しい版は、MuninnLog 側の PR で取り込む。その PR では CI の無線機テストに合格することを条件にする |
| 要望 | MuninnLog 側で必要になった機能（未決事項 Q10：PTT の送信時間の監視、CW 送信、ライブラリ読み込み先の API 指定など）は、HamlibComponent 側の Issue として管理する |

### HuginnEngine

| 項目 | 方針 |
|---|---|
| 通信仕様 | `MuninnLog/docs/interfaces/huginn-v1.md` に書き、版を管理する。変更は両方の開発者が合意してから行う |
| 模擬エンジン | MuninnLog のテスト用に、通信仕様どおりに応答する模擬エンジンを作る。実エンジンが無くても M1〜M2 を進められるようにする |
| 契約テスト | 通信仕様に沿った試験項目を共通で持ち、模擬エンジンと実エンジンの両方に実行する |
| 接続試験 | M2 以降、実エンジンの版を固定して接続試験を行う |

## 10. 文書と意思決定

| 種類 | 置き場所 | 規則 |
|---|---|---|
| 開発方針 | `docs/00_DEVELOPMENT_POLICY.md` | 決定事項と未決事項の一覧の正本。変更は開発者の承認が必要 |
| 設計文書 | `docs/01〜05` | コードと同じ PR で更新する |
| 設計判断の記録（ADR） | `docs/adr/NNNN-<題名>.md` | 1 判断 1 ファイル。背景、選択肢、決定、結果を書く。決定したら 00 の決定事項に追記する |
| 通信仕様 | `docs/interfaces/` | 版番号を付ける |
| 状況報告 | GitHub の Milestone と Issue | 事実だけを書き、CI 実行や PR へのリンクを付ける。文書で進捗を主張しない |

未決事項は Issue として登録し、期限を付ける。期限までに判断材料（試作、測定、調査）を揃え、開発者が決める。

## 11. リリース

| 段階 | 時期 | 対象 | 条件 |
|---|---|---|---|
| 夜間ビルド | M0 以降、毎日（ワークフローは未作成） | 開発者 | CI 合格 |
| アルファ | M1 の終わり | 開発者本人の日常運用 | M1 の品質ゲート、既存ログを取り込める、QSO を失わない |
| ベータ | M2 の終わり | 協力してくれる JA コンテスター数名 | 実際のコンテストで 1 回運用し、電子ログを提出できる |
| 1.0 | M4 の終わり（予定） | 一般公開 | 品質ゲートのすべて、署名・公証済みの配布物、利用者向け文書 |

- **版番号：** セマンティックバージョニング（1.0 までは 0.x）。データ形式（SQLite スキーマ、Yata Logic、通信仕様）には、それぞれ独立した版番号を持たせる。
- **フィードバック：** GitHub の Issue と Discussions で受け付ける。
- **クラッシュ報告：** 利用者の同意がある場合だけ送る（決定事項 D11）。

## 12. 計測する指標

| 指標 | 目的 |
|---|---|
| master の CI 合格率 | 常に 100% を保つ。赤くなったら最優先で直す |
| PR がマージされるまでの日数 | 作業の滞留を見つける |
| マイルストーンごとの、予定タスク数と完了タスク数 | 計画の精度を上げる |
| リリース後に見つかった不具合の数 | テストの抜けを見つける |
| 性能測定の値 | 退行を見つける |

M0 の完了条件：3 OS の CI で中核ライブラリと `muninn-cli` がビルド・テストに合格し、ADIF ファイルを読み込んで SQLite に保存し、ADIF に書き戻せること。

| # | タスク | 依存 | 完了条件 |
|---|---|---|---|
| T0 | リポジトリ設定（ブランチ保護、squash マージ） | — | 開発者が GitHub の設定で実施 |
| T1 | ディレクトリの骨組み、`CLAUDE.md` / `AGENTS.md`、PR テンプレート | — | 予定構成（[README](../README.md)）のディレクトリと指示書がある |

| T3 | テストの仕組み（FPCUnit の採用確認、CI からの実行、結果の出力） | T2 | サンプルテストが 3 OS の CI で実行される |

## 14. リスクと対策

| リスク | 対策 |
|---|---|
| 開発者 1 名がレビューの律速になる | PR を小さく保つ。AI レビューで一次確認を済ませる |
| macOS の CI と配布（署名・公証）が難航する | M0 で CI、M1 で配布を先に通す。後回しにしない |
| HuginnEngine の開発が遅れる | 模擬エンジンで MuninnLog を先に進める。FT8 は WSJT-X 連携で代替できる |
| 規約定義の作成・保守が追いつかない | Yata Logic を宣言的に書ける形にし、協力者が書けるようにする。規約ごとにゴールデンテストを必須にする |
| AI エージェントの出力の品質がばらつく | 第 6 節のルールと、CI・ブランチ保護による機械的な歯止め |
| 範囲が広がりすぎる | 00 の「後回しにするもの」を守る。範囲の追加は未決事項として扱い、開発者が判断する |
