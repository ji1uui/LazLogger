# 0005: 日本の市郡区コード（JCC / JCG / 区）の参照データ

- 状態：提案（この ADR を含む PR のマージで決定。実装は M1）
- 日付：2026-10-18
- 関連：[00_DEVELOPMENT_POLICY.md](../00_DEVELOPMENT_POLICY.md) 決定事項 D17、[ADR 0004](0004-adif-import-export.md)、[参考資料](../references/README.md)

## 背景

JA のコンテストやアワード（AJA、JCC、JCG）では、交信相手と自局の市・郡・区を正しく記録し、確かめる必要がある。
ADIF 3.1.8 は、これらを `CNTY` / `MY_CNTY` のコードとして定めている（III.B.22）。

| 区分 | 現行のコード数 | 削除済み | 書式 |
|---|---|---|---|
| 市（JCC） | 815 | 99 | 都道府県 2 桁 ＋ 2 桁または 4 桁 |
| 区（WAKU） | 175 | 7 | 都道府県 2 桁 ＋ 市 2 桁 ＋ 区 2 桁 |
| 郡（JCG） | 379 | 244 | 都道府県 2 桁 ＋ 3 桁 |

次の 3 つの理由から、書式の検査（ADR 0004）だけでは足りない。

- 桁数だけでは区分が決まらない。100101 は 6 桁だが、区ではなく JCC（東京都千代田区）である。
- 市町村の合併や政令指定都市の区の新設・廃止で、コードの有効期間が変わる。ADIF II.C は、削除された値を有効期間内の QSO に限って認めている。
- JARL のリストは、区・JCG・JCC で更新日が別々になっている。

## 決定

1. **参照データ**
   - JCC・JCG・区のマスタを、アプリ内部の参照データとして持つ。ログの DB とは分ける。
   - 1 件の属性：

| 属性 | 内容 |
|---|---|
| Scheme | `jcc` / `jcg` / `ku`（固定の文字列コード） |
| Code | ADIF の `CNTY` の値（文字列。先頭のゼロを含む） |
| PrefectureCode | ADIF の `STATE` の値（01〜47） |
| Name / NameJa | 英字名と日本語名 |
| ValidFrom / ValidTo | 有効期間（UTC の日付。不明なら空） |
| SourceVersion | 元にしたリストとその更新日 |

2. **判定の順序**
   1. DXCC が 339 であることを確かめる。
   2. 参照データでコードを探す。区分（JCC・JCG・区）は参照データから決め、桁数からは決めない。
   3. 交信日時で有効期間を確かめる。
   4. `STATE` と一致するかを確かめる。
3. **結果の扱い**
   - 照合の結果は、QSO の値を変えずに、検証の状態として記録する。
   - 照合できないコードや有効期間外のコードも、元の値のまま保持する。
   - 過去の QSO のコードを、現在のコードへ自動で書き換えない。
4. **妥当性の区別**：ADIF として妥当かどうかと、個々のアワードで有効かどうかは、分けて判定する。アワードの規則は Omoikane の規約パッケージで扱う。

## 未決の点（M1 の前に決める）

- **再配布の条件：** JARL のリストから作ったデータをアプリに同梱してよいか。JARL に確認する。
- **データの作り方：** 共有された JARL のリスト（`docs/references/`）から変換するか、ADIF の公開している列挙から作るか。
  - JARL のリストの消滅日は書式が揃っていない（`"Jan.31.1967"`、閉じ引用符の欠落など）。
  - 名称の綴りに誤りがある。
  - そのため、変換時の検証が必要。
- **更新の配り方：** アプリの更新に含めるか、データだけを更新できるようにするか。

## 結果

- M1 で、参照データの形式（SQLite の別ファイル、または同梱の CSV）と取り込みのツールを作る。
- ADR 0004 の書式の検査は、参照データができるまでの最低限の検査として残す。
