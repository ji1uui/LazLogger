# 0009: 画面の技術（LCL＋独自描画）

- 状態：提案（この ADR を含む PR のマージで決定）
- 日付：2026-10-19
- 関連：M0 タスク T10（[05_DEVELOPMENT_PROCESS.md](../05_DEVELOPMENT_PROCESS.md) 第 13 節）、[00_DEVELOPMENT_POLICY.md](../00_DEVELOPMENT_POLICY.md) 旧未決事項 Q2・決定事項 D21、[02_PRODUCT_STRATEGY.md](../02_PRODUCT_STRATEGY.md) 第 5 節

## 背景

画面の技術は未決事項 Q2 だった。候補は次の 2 つ（[02](../02_PRODUCT_STRATEGY.md) 第 5 節）。

- (a) LCL＋独自描画
- (b) Pascal の本体＋Web 技術の画面（WebView）

推奨は (a) で、決める前に入力画面とバンドマップだけを試作して確かめることになっていた。開発者の指示（2026-10-19）は「LCL ベースでマルチ OS を前提に進める」。

試作で確かめたいことは次の 4 点。

- 3 OS（Windows / macOS / Linux）で同じコードがビルドでき、動くか
- キー入力から画面の更新までが十分に速いか（コンテストの入力で遅れを感じないか）
- 独自描画の部品（バンドマップ）を、必要な速さと見た目で作れるか
- 画面のロジックを LCL から切り離し、画面なしでテストできるか

## 選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **(a) LCL＋独自描画** | 1 つの言語と 1 つのビルド。キー入力の経路が短い。OS 標準の入力欄（IME、アクセシビリティ）をそのまま使える | 凝った部品は自作する。Windows のダークモードは標準の部品では弱い |
| (b) WebView | デザインの自由度が高い。他の端末へ展開しやすい | 2 つの技術を抱える。OS ごとの WebView の違い（Windows の WebView2 の配布、macOS の WKWebView）。Pascal と JavaScript の間の通信が入力のたびに挟まる |

## 試作

| 部分 | 内容 | LCL |
|---|---|---|
| `TQsoEntryPresenter`（`Muninn.UI.QsoEntry`） | コールサインの正規化と検査、パーシャルチェック、同じバンド・モードの重複、Enter での記録 | 使わない（単体テストあり） |
| `TBandmapModel`（`Muninn.UI.Bandmap`） | 周波数と画面上の位置の変換、ラベルが重ならない配置、ズーム、スクロール、クリックした局の判定 | 使わない（単体テストあり） |
| `TBandmapControl`（`Muninn.UI.BandmapView`） | `TCustomControl` の `Paint` で描く。ダブルバッファー。大きさはフォントに合わせて決め、DPI に追従する | 使う |
| `TMainForm`（`Muninn.UI.MainForm`） | 入力欄、パーシャルチェックの一覧、交信の一覧、バンドマップ。部品の配置とイベントの転送だけを行う | 使う |
| `muninn-gui`（`app/gui`） | デモデータで起動する。`--measure` で反応速度を測る。`--light` でライトテーマ | 使う |

- 交信済みの局は色に加えて斜体で、強調する局は色に加えて枠で示す（色だけに頼らない）。
- 試作の途中で、5000 局を描くと 1 回に 70〜400 ms かかることが分かった。
  - 原因 1：画面の外に押し出されたラベルまで描いていた。下端で描画を止め、「+N more below」と表示するようにした。
  - 原因 2：初回の並べ替えが挿入ソートだった。クイックソートに替えた。
  - どちらも直したあとは、1.5 ms 前後になった。
- 交信済みの表示は、バンドとモードで決まる。記録したときとモードを変えたときに、全局について記録を問い合わせ直す。5000 局で記録（Enter）に約 5 ms かかる（1 フレームに収まる）。

## 測定

`muninn-gui --measure` は、実際の画面のコールサイン欄に 1 文字ずつ入力し、バンドマップが再描画されるまでの時間を測る。描画は `Paint` の中の時間と、無効化から描画完了までの時間の両方を測る。

結果（ms。CI のランナーと Xvfb は実機ではないため、目安として扱う）：

| 項目 | Linux（gtk2、Xvfb、手元） |
|---|---|
| 起動から最初の描画まで | 187 |
| キー入力の処理（中央値 / p95） | 0.58 / 0.84 |
| キー入力 → バンドマップの再描画（中央値 / p95） | 2.39 / 3.54 |
| バンドマップの描画、1000 局（中央値 / p95） | 0.82 / 1.26 |
| バンドマップの描画、5000 局（中央値 / p95） | 1.33 / 1.48 |
| パーシャルチェック、10 万局（中央値 / p95） | 3.23 / 4.23 |
| 記録（Enter）（中央値 / p95） | 4.70 / 5.43 |

macOS と Windows の値は CI の GUI ジョブの結果から追記する。

目標は、キー入力から画面の更新まで 1 フレーム（16 ms）以内とした。

## 決定

1. 画面は **LCL＋独自描画**で作る（選択肢 (a)）。WebView は使わない。
2. **Presenter と View を分ける**
   - 画面の判断（検査、パーシャルチェック、重複、配置の計算）は LCL に依存しない Presenter とモデルに置き、FPCUnit で試験する。
   - LCL の画面は、部品の配置、描画、イベントの転送だけを行う。
3. **独自描画の部品**は `TCustomControl` の `Paint` で描く。
   - 寸法はフォントから決める（`Scale96ToFont`）。
   - 色はテーマ（`TUiTheme`）から取る。ダーク / ライトの 2 つを用意する。
   - 色だけで状態を区別しない。
4. **ビルド**
   - GUI は `.lpi` を lazbuild でビルドする（`scripts/build-gui.sh`）。
   - CI では次の方法で Lazarus を用意する。
     - Linux / macOS：Lazarus 4.4 の公式ソース（SHA-256 を固定）から `make lazbuild` でビルドし、キャッシュする。ADR 0001 で、この 2 OS の FPC は apt / Homebrew から入れていて、LCL を含まないため。
     - Windows：setup-lazarus を使う。
   - LCL のウィジェットセットは、Linux が gtk2、macOS が Cocoa、Windows が win32。
5. **反応速度を CI で毎回測る**
   - GUI ジョブで `--measure` を実行し、結果をジョブの要約と成果物に残す。
   - 描画が 2 秒以内に起きなければ失敗にする。
   - 速さの数値ではまだ失敗にしない。ランナーの性能が揃わないため。

## 結果

- 未決事項 Q2 を解消する（D21）。
- `src/ui` は、LCL を使わない Presenter とモデル、LCL を使う View に分かれる。単体テストのビルドは `-Fusrc/ui` を含み、LCL を使うユニットは単体テストから参照しない。
- macOS で GUI を配布するには、`.app` の作成と署名・公証が別に必要（配布の作業で扱う）。

**見直す条件：**

- 実機での測定で、目標（16 ms）を大きく超える操作が見つかったとき
- LCL の標準部品では足りない画面（タブレット向けなど）が必要になったとき
- Windows のダークモードの対応が、利用者の要望に対して不十分なとき
