# 0004: ADIF の読み込みと書き出し

- 状態：決定（2026-10-18 にマージ）
- 日付：2026-10-18
- 関連：M0 タスク T6（[05_DEVELOPMENT_PROCESS.md](../05_DEVELOPMENT_PROCESS.md) 第 13 節）、[00_DEVELOPMENT_POLICY.md](../00_DEVELOPMENT_POLICY.md) 決定事項 D16、[ADIF 3.1.8](../references/ADIF_3.1.8_excerpt.txt)

## 背景

ADIF はほかのロガーやオンラインサービスとの交換形式で、MuninnLog の取り込みと書き出しの基本になる（D5）。
実際のファイルには、仕様どおりでないものもある。

- 非 ASCII の文字（日本語の名前・QTH）を ADI に書いたファイルがある。
- データ長を、バイト数ではなく文字数で書くロガーがある。
- 廃止された（import-only の）モードを使ったファイルがある。

取り込みで交信記録を失わないことを最優先にする（00 第 3 節）。

## 決定

1. **形式と置き場所**
   - ADI 形式（ADIF IV.A）を扱う。ADX（XML）は対象外とし、必要になったら別に決める。
   - 読み書きは `src/core` に置き、ファイルの読み書きはしない。
     - `Muninn.Core.Adif`：文書のモデル、読み込み（`ReadAdi`）、書き出し（`WriteAdi`）
     - `Muninn.Core.AdifQso`：ADIF のレコードと QSO（`TQsoRecord`）の変換
     - `Muninn.Core.AdifModes`：ADIF 3.1.8 のモード・サブモードの一覧（III.B.10）
2. **文字コードとデータ長**
   - 文字列は UTF-8 で扱う。
   - データ長は、書き出しでは常にバイト数で書く。
   - 読み込みでは、バイト数として読む。ただし、値に非 ASCII の文字があり、バイト数では合わないが文字数では合う場合は、文字数として読み、警告を出す。
     - 「合わない」とは、文字の途中で切れる、または次のタグまでに空白以外の文字が残ること。
     - フィールドの間の文字（ADIF IV.A.6）が、非 ASCII の値の直後に空白を挟まずに続く場合は区別できない。値の末尾を失わないことを優先して、文字数として読む。
   - データ長は 10 進の数字だけを受け付ける（`$4` や `0x4` はエラー）。
   - 最初のタグの前が空行や空白だけの場合は、`<EOH>` タグがあればヘッダーあり、無ければヘッダー無しとして読む（IV.A.3 は先頭の 1 文字で決めるが、QSO もヘッダーの定義も失わないため）。
   - 書き出しでは、ヘッダーの文字列に `<` があるか、空白だけの場合は、既定の文字列（`ADIF export`）を書く。
   - UTF-8 として正しくない値（Shift_JIS など）は、バイト列のまま残して警告を出す。Shift_JIS のファイルの変換は、実際の出力例を入手してから扱う。
3. **値は失わない**
   - フィールド名は大文字に揃える。値は見つけたとおりに保持する（`CNTY` の `0101` のような先頭のゼロも残す）。
   - 解釈できない値（帯域外の `BAND`、数値でない `FREQ` など）は、元の ADIF 名のまま `OtherFields` に残し、警告を出す。
   - アプリ定義フィールド（`APP_...`）とユーザー定義フィールドは、データ型の指示子も含めて残す。ユーザー定義フィールドを有効に保つため、書き出しでは取り込み元の `USERDEFn` をヘッダーに写す。
   - 同じフィールドが 1 つのレコードに 2 回あれば、最初の値を残して警告を出す。
4. **値の範囲**
   - `MODE` / `SUBMODE` は、列挙に無い値でも、表示できる ASCII 文字であれば保持し、警告を出す（例：`OLIVIA 8-250`）。
5. **QSO として必要なもの**
   - `CALL`、`QSO_DATE`、`TIME_ON`、`MODE` が無いレコードは QSO にしない。エラーとして報告し、ほかのレコードの取り込みは続ける。
   - `QSO_DATE` は ADIF の Date 型どおり 1930 年以降とする。
6. **正規化（書き出し）**
   - 項目の順序：型付きの項目（`CALL`、日時、`BAND`、`FREQ`、`MODE`、`TX_PWR` など）を先に固定の順序で書き、その後に `OtherFields` を記録された順に書く。
   - 周波数は整数 Hz、出力は整数 mW で保持する。1 Hz より細かい値は四捨五入し、警告を出す。
   - `FREQ` は MHz で、末尾のゼロを付けずに書く（`14.0740` → `14.074`）。
   - `TIME_ON` / `TIME_OFF` は秒まで書く（`1305` → `130500`）。`TIME_OFF` には常に `QSO_DATE_OFF` を付ける。
   - `QSO_DATE_OFF` が無い（空の値も含む）とき、終了時刻が開始時刻より前なら、終了は翌日とみなす。比較は `TIME_OFF` の精度で行う（`TIME_OFF` が `1200` なら `TIME_ON` の `120030` より前ではない）。翌日が 9999-12-31 を越える場合は、元の値のまま残して警告を出す。
   - `BAND` は小文字の ADIF 名で書く。`BAND` が無く `FREQ` があれば、`FREQ` から求める。
   - import-only のモードは、ADIF II.B に従って `MODE` ＋ `SUBMODE` で書く（`C4FM` → `DIGITALVOICE` / `C4FM`）。
7. **日本の行政区分**
   - `STATE` / `MY_STATE` と `CNTY` / `MY_CNTY` には、ADIF III.B.12 と III.B.22 のコードをそのまま入れる。接頭辞は付けず、先頭のゼロも削らない。JCC / JCG を表す独自のフィールドは作らない。
   - DXCC が 339 の場合は、書式だけを確かめ、合わなければ警告を出す。
     - `STATE` が 01〜47 であること
     - `CNTY` が 4〜6 桁の数字であること
     - `CNTY` の先頭 2 桁が `STATE` と一致すること
   - JCC / JCG / 区のリストとの照合と有効期間の判定は、[ADR 0005](0005-japanese-subdivision-reference-data.md) の参照データで行う。
8. **往復の確認**
   - ゴールデンテスト（`tests/golden/adif/`）で確かめる。
     - 取り込み → 書き出しの結果が、期待するファイルと一致すること
     - 期待するファイルを取り込み直して書き出しても、変わらないこと

## 結果

- `CNTY` の値が JCC・JCG・区のどれに当たるかは、書式だけでは決められない。たとえば 100101 は 6 桁だが、区ではなく JCC（東京都千代田区）である。区分は ADR 0005 の参照データで決める。
- 書き出しが仕様から外れる点がある。非 ASCII の文字を含む値を ADI に書く。これは日本のログで実際に使われているためである。
- ゴールデンテストのデータは合成したもの。WSJT-X の出力形式と日本の国内ログの典型を模している。実際のロガー（Hamlog など）の出力例を入手したら、ゴールデンテストに加える。個人情報は匿名化する。

**見直す条件：**

- ADX 形式や Shift_JIS のファイルを扱う必要が出たとき
- ADIF の新しい版でモードやフィールドが変わったとき（`Muninn.Core.AdifModes` を作り直す）
