## 1. ビジョン

日常の交信、コンテスト、デジタル / 電信運用、POTA / SOTA を **一つのログブック** でつなぐ。
Windows と macOS で同じ体験を提供し、モダンなデザインで CTESTWIN / Turbo Hamlog など旧来のアプリと差別化する。
JA コンテスター全般を主な利用者とし、海外のコンテストや運用にも対応する。

## 3. 開発原則

1. **ログブックが中核、エンジンは外部。** MuninnLog は「交信を失わない・正しく記録する・使いやすい」ことに集中する。信号処理は HuginnEngine、無線機制御は HamlibComponentに任せる。
2. **中核は GUI から独立させる。** ドメイン・保存・規約エンジンは LCL に依存しないライブラリとして作り、GUI と CLI の両方から同じものを使う。CLI はテストと自動化の入口になる。
3. **縦に薄く、動くものから。** 基盤や文書を先に積まず、各段階で「実際に使える機能」を一本通す。完了条件は文書の更新ではなく、動く機能と合格したテストとする。
4. **受信は止まっても続行、送信は安全側に倒す。** 受信系の障害ではログ入力を止めない。送信（PTT、CW キーイング）は異常時に必ず止める。
5. **自動補正は元に戻せる。** HuginnEngine の文脈補正や将来の AI 補完の結果は、生の値と区別して保存し、利用者が却下・取り消しできるようにする。
6. **データ形式は互換性を最優先。** QSO 項目の意味は ADIF 3.x に揃え、保存形式は版管理とマイグレーションを持つ。Yata Logic のパッケージ形式と `THuginnInterface` の通信仕様も版を持つ。
7. **CI 合格をマージ条件にする。** `Lazarus/` で起きたマージ事故（[01](01_CURRENT_STATE_REVIEW.md) 第 2 節）を繰り返さない。Windows / macOS / Linux のマトリクスで build とテストを回す。

## 4. 2 つのアイデアの統合

### 4.1 MuninnLog 構想書 v4.0 から

| 項目 | 扱い | 理由・補足 |
|---|---|---|
| HuginnEngine への信号処理の分離 | **採用** | 原則 1 と一致。既存 `Lazarus/` の音声リングバッファや RTTY 試作は、MuninnLog ではなく HuginnEngine 側の資産として扱う |
| `THuginnInterface` | **採用・具体化** | 通信仕様を版管理し、HuginnEngine は別プロセスで動かす案を推奨（[04](04_ARCHITECTURE.md) 第 3 節）。エンジンの異常終了でログが巻き込まれない |
| `TAudioSubsystem`（PortAudio で音声を取り込み、Huginn へ渡す） | **変更** | 音声は高頻度データなので、アプリとエンジンの境界を流さない。音声入出力は HuginnEngine が直接持ち、MuninnLog はデバイスの選択 UI とデコード結果の受信だけを担う |
| `TRigControlSubsystem`（Hamlib） | **採用** | D3 の HamlibComponentを使う。PTT を含む無線機の操作は一か所（単一の所有者）からだけ行い、HuginnEngine の送信要求もここを経由する |
| `TLoggingSubsystem`（SQLite） | **採用** | D10 |
| `TPluginManager`（JSON の規約・アワード定義） | **統合** | Omoikane の Yata Logic と一本化する |
| `TScriptEngine`（Lua / Python） | **変更・後回し** | 規約の計算は Yata Logic の Pascal Script で行う。汎用の自動化スクリプトは需要を見て後で判断する。Python の同梱は macOS 配布の負担が大きい |
| `TPrivacyManager`（同意管理、データ主体の権利） | **採用・範囲を明確化** | 対象は利用者自身のデータと外部への送信（オンライン同期、PSKReporter、GPS、CW 学習データ）。交信相手のコールサインを含む QSO 記録そのものは、ログの完全性とコンテスト提出の要件があるため削除権の対象外とし、その旨を明示する |
| `TGpsInterface`（NMEA） | **採用** | POTA / SOTA の運用地（Location）の自動入力に使う。同意が前提 |
| 統合操作画面（ウォーターフォール、ログ入力、送受信、クラスタ） | **採用** | デジタル運用モードの画面として。ウォーターフォールは HuginnEngine からの表示用データで描画する |
| マルチプロファイル（運用者・運用地のスナップショット） | **採用・拡張** | [03_DATA_MODEL.md](03_DATA_MODEL.md) の Person / Station / Location / Station Facility / Operation として具体化済み |
| ロードマップ（Phase 1–5 が信号処理先行） | **変更** | ログ中核を先に作る。HuginnEngine は通信仕様を早期に固め、並行して進める（第 6 節） |

### 4.2 Omoikane 実装仕様書から

| 項目 | 扱い | 理由・補足 |
|---|---|---|
| コンテストの規約適用・得点計算システム | **採用** | MuninnLog 内のコンテスト機能 Omoikane として |
| Yata Logic（.ylg = ZIP、`rules.json` ＋ Pascal Script） | **採用** | 規約定義とアワード定義の共通形式にする。宣言的に書ける部分は `rules.json`、書けない部分だけをスクリプトにする |
| SHA-256 とデジタル署名による検証 | **採用・信頼モデルを追加** | 公式に配布するパッケージは署名必須。利用者が自作したローカルのパッケージは、署名なしでも警告付きで使えるようにする（自作・共有できることが価値の一つのため） |
| ログエディタ（グリッド、リアルタイム検証、赤枠とツールチップ） | **採用** | コンテスト後処理の画面として |
| Undo / Redo | **採用** | QSO の修正履歴（Revision）と同じ仕組みで実現する。永続化される変更は履歴として残る |
| ADIF / CSV / Cabrillo / JSON の入出力、出力プレビュー | **採用** | JARL 電子ログも加える |
| CLI（`--load`、`--export`、`--plugin`、`--quiet` など） | **採用** | 中核ライブラリを使う別の起点 `muninn-cli` として。再計算・検証・出力のバッチ処理、ゴールデンテストに使う |
| メインダッシュボードを中心とした画面遷移（3 クリック以内） | **一部採用** | コンテスト後処理と管理系の画面に適用する。運用中の入力画面はキーボード中心で、ダッシュボードを経由しない |
| 運用中のリアルタイム入力 | **追加** | Omoikane 仕様に無いため、[02](02_PRODUCT_STRATEGY.md) の入力画面（ESM、バンドマップ、パーシャルチェック）で補う |
| `config.ini` | **一部採用** | アプリの設定（画面配置など）に限る。プロファイルや運用データは SQLite に保存する |
| Observer パターン（`TDataManager`） | **採用** | UI への通知は UI スレッドで行う |
| スクリーンリーダー対応（ARIA 属性）、高コントラストテーマ | **採用・表現を修正** | LCL には ARIA が無いため、OS 標準部品のアクセシビリティ情報で対応する。独自描画の部品にはアクセシビリティ情報を個別に実装する |
| 単体テストのカバレッジ 80%、静的解析 | **採用・要確認** | 静的解析ツールは FPC で実際に使えるものを選定する（仕様書の「PascalLint」は存在と適合性を確認する） |
| オンライン更新（規約パッケージの自動取得） | **採用（後の段階）** | 署名検証とセットで |
| JARL 等の公式データベースとの連携 | **採用（後の段階）** | 提供条件の確認が前提 |
| モバイル対応 | **後回し** | POTA / SOTA の現場運用で価値が高い。デスクトップ版の安定後に、同期と確認に絞って検討する |
| AI によるログ補完・音声入力 | **研究扱い** | 原則 5 に従い、補正前の値を必ず残す |
| ロードマップの日付（2025 年 Q3〜） | **破棄** | 既に過去の日付のため、第 6 節で置き換える |

## 5. 範囲

### 最初に作るもの

- ログブック（SQLite）、プロファイル（Person / Station / Location / Station Facility / Operation）
- QSO の入力・修正・検索、ADIF の入出力、Hamlog データの取り込み、バックアップ
- HamlibComponentによる周波数・モードの連動
- Omoikane: Yata Logic ローダー、重複チェック、得点・マルチ、Cabrillo / JARL 電子ログ出力、コンテスト後のログエディタ
- `THuginnInterface` v1（デコード結果の受信、ウォーターフォール表示、送信要求）と、WSJT-X の UDP 連携
- `muninn-cli`

### 後回しにするもの

マルチオペ、SO2R、クラスタ、アワード集計、QSL 印刷、オンライン同期、プラグインのオンライン更新、汎用スクリプト、モバイル、AI 補完

## 6. ロードマップ

各段階の完了条件は「その段階の機能が Windows と macOS で動き、テストが CI で合格していること」とする。

| 段階 | 内容 | 並行作業（HuginnEngine） |
|---|---|---|
| **M0 基盤** | ディレクトリと CI（Win / mac / Linux）、中核ライブラリと `muninn-cli` の骨組み、SQLite スキーマ v1、ADIF 入出力、ゴールデンテストの仕組み | `THuginnInterface` 通信仕様 v1 を両チームで合意し、模擬エンジンを作る |
| **M1 日常ログ** | 入力画面、コールサイン情報カード、Hamlib 連動、プロファイル管理、Hamlog 取り込み、バックアップ | エンジン単体での FT8 / RTTY デコード |
| **M2 Omoikane v1** | Yata Logic 形式 v1、国内 1 本（ALLJA1 など）と海外 1 本（CQ WW など）の規約、重複チェック、得点、Cabrillo / JARL 電子ログ、ログエディタと Undo / Redo、CLI での再計算 | 実エンジンとの接続試験 |
| **M3 デジタル運用** | `THuginnInterface` 実接続、ウォーターフォール、デコード一覧からの記録、WSJT-X 連携、プライバシー同意 UI（PSKReporter など） | CW デコード、送信制御 |
| **M4 運用中のコンテストと移動運用** | ESM、バンドマップ、パーシャルチェック、CW キーヤー、POTA / SOTA（GPS、複数公園、公園別出力） | 高度 CW デコード（学習機能は同意前提） |
| **M5 拡張** | オンライン同期、アワード（Yata Logic）、規約パッケージの署名配布とオンライン更新、テーマエディタ、クラスタ、マルチオペ | |

M1 と M2 の順序は未決事項 Q1 で決める。

作業の進め方（イテレーション、PR、CI、M0 のタスク分解）は [05_DEVELOPMENT_PROCESS.md](05_DEVELOPMENT_PROCESS.md) を参照。

## 7. 品質ゲート

| ゲート | 内容 |
|---|---|
| ビルド | Windows / macOS / Linux の CI でビルドが通る。CI 合格がマージ条件 |
| 単体テスト | 中核ライブラリ（ドメイン、規約エンジン、入出力）のカバレッジ 80% を目標 |
| ゴールデンテスト | 規約ごとに、QSO ごとの重複・得点・マルチと合計点を固定データで照合する。ADIF / Cabrillo / JARL 電子ログは往復変換で照合する |
| 結合テスト | Yata Logic の読み込み（署名不正、破損を含む）、SQLite のマイグレーション、`THuginnInterface` の模擬エンジン |
| 障害試験 | 電源断・強制終了・ディスク満杯で QSO を失わないこと、HuginnEngine の異常終了でログ入力が止まらないこと、送信系の異常で PTT が必ず切れること |
| 性能 | 入力から画面反映までの遅延、10 万件以上のログでの検索・重複チェック・得点再計算の時間を計測し、基準値との比較で退行を検出する |
| UX | キーボードだけでの操作、ダーク / ライト、高 DPI、日本語・英語、スクリーンリーダー |
| 配布 | Windows の署名、macOS の署名・公証、クリーンな環境での起動 |

実行していない検証は合格と報告しない。
