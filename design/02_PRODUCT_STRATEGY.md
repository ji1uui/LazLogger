# 製品方針

## 1. 狙い

いま JA の多くの局は、目的ごとにソフトを使い分け、ADIF などで手作業の受け渡しをしている。

- コンテスト: CTESTWIN、zLog
- 日常の記録: Turbo Hamlog
- FT8: WSJT-X / JTDX
- POTA / SOTA: スマートフォンのアプリ

新アプリは **日常ログ・コンテスト・POTA/SOTA を一つのログブックでつなぐ** ことを価値の中心に置く。
コンテスト中の QSO がそのままアワード集計や QSL 管理に入り、移動運用の記録がそのまま公園別の提出物になる。

## 2. 製品の骨格

```text
Logbook（全 QSO。項目の意味は ADIF 3.x に揃える）
 ├─ Operation: 日常運用
 ├─ Operation: ALLJA1 2027        … 規約エンジン・重複チェック・得点・JARL 電子ログ
 ├─ Operation: CQ WW DX CW        … Cabrillo
 ├─ Operation: POTA JA-0001 + JA-0002
 └─ Operation: SOTA JA/TK-001
```

各 Operation は「どの局（Station）として、どこで（Location）、何の設備で（Facility Setup）、誰が運用するか」を指定する。
詳細は [03_DATA_MODEL.md](03_DATA_MODEL.md)。

## 3. 自前で作るものと連携するもの

| 領域 | 方針 | 理由 |
|---|---|---|
| 無線機制御 | 自前の Hamlib コンポーネント | 決定事項 D3 |
| FT8 / FT4 | WSJT-X / JTDX と UDP で連携（QSO 記録、デコード結果、相手局の強調表示） | 主要なロギングアプリはすべてこの方式。自前デコーダは費用対効果が合わない |
| RTTY / PSK | 最初は fldigi（XML-RPC）と連携。Windows では MMTTY にも対応 | MMTTY は Windows 専用。自前の RTTY は将来の選択肢として残す |
| CW 送信 | 自前（WinKeyer、Hamlib のモールス送出、ファンクションキーのメッセージ） | コンテストの操作感を左右する中核 |
| CW 解読 | 後回し（CW Skimmer / RBN のスポットで代用） | |
| 規約・得点・重複チェック | 自前（データで規約を定義するエンジン） | 差別化の中核 |
| QSL / アップロード | LoTW、eQSL、Club Log、QRZ、POTA / SOTA 向け出力、JARL 電子ログ | 連携先の仕様に合わせる |
| 局情報（DXCC、JCC / JCG） | ローカルのデータ＋外部の参照サービス | JA 向けの価値が高い |

## 4. 他のアプリから取り入れる点

| 参考アプリ | 取り入れる点 |
|---|---|
| CQRLOG | 日常ログに必要な機能の一覧（DXCC・アワード、QSL 管理、クラスタ、グレイライン、オンラインサービス、バックアップ）、rigctld のプロセス管理、Lazarus で Linux / macOS を扱う知見。GPL のためコードは使わず、機能と設計の参考に留める。外部 DB（MariaDB）前提でインストールが難しい点は反面教師 |
| N1MM Logger+ | Enter キーで送信と記録を進める入力操作（ESM）、バンドマップ、パーシャルチェック / コールヒストリー、UDP でのQSO・無線機情報の配信、マルチオペ |
| Win-Test / DXLog.net | キーボードだけで完結する速さ、ネットワーク越しのマルチオペ同期 |
| Log4OM 2 | アワード集計の仕組み、多数のオンラインサービスとの同期 |
| MacLoggerDX / RUMlog | macOS ユーザーが期待する操作感と地図表示 |
| JTAlert / GridTracker | FT8 のデコード結果に「未交信」「新しい DXCC・JCC」を重ねて知らせる機能、地図表示 |
| Ham2K PoLo / HAMRS | POTA / SOTA の運用テンプレート、公園番号の検索、複数公園の同時アクティベート、セルフスポット、オフライン運用、公園ごとの出力 |
| Wavelog / Cloudlog | Web ログブックとの同期 |
| CTESTWIN / Turbo Hamlog（差別化の相手） | JCC / JCG・市郡区番号の扱い、JARL 電子ログ、Hamlog データの取り込み、QSL カード印刷。乗り換えの障壁を下げるために必須 |

ライセンスは参照前に各リポジトリで確認する。

## 5. デザイン原則

1. キーボード中心で、探しやすい。入力欄の操作は運用の種類を変えても同じ。全機能をコマンドパレットから検索できる
2. コールサイン情報カード。過去の交信、JCC / DXCC、公園・サミット、必要なマルチ・アワードを 1 枚に集約する。手元のデータは即座に、ネット参照は後から表示し、入力を止めない
3. 運用の種類ごとに画面を切り替える（Run / S&P / FT8 / POTA / 日常 / コンテスト後処理）
4. ダーク / ライト、高 DPI、日本語・英語、アクセシビリティを最初から前提にする
5. QSO を絶対に失わない。状態表示は「接続中」だけでなく、最後に成功した時刻や待ち件数まで見せる
6. オフラインで動くことを基本とし、クラウド連携は任意にする
7. 送信中の自局コールを常に明示し、誤ったコールでの記録を防ぐ

### 画面の技術（未決事項 Q2）

| 選択肢 | 長所 | 短所 |
|---|---|---|
| (a) LCL＋独自描画の部品群（BGRABitmap など） | キー入力が速く、構成が単純 | 部品を自作するコストがかかる。Windows のダークモードは標準では弱い |
| (b) Pascal の本体＋Web 技術の画面（WebView） | デザインの自由度が高く、タブレット等への展開もしやすい | 2 つの技術を抱える。入力の反応速度と、両 OS での WebView 連携が課題 |

推奨は (a)。決定前に、入力画面とバンドマップだけを試作して判断する。

## 6. リリース段階

| 段階 | 内容 | 目的 |
|---|---|---|
| R0 基盤 | `Lazarus/` master の修復、データモデル、保存方式、ADIF の入出力、Hamlog データの取り込み | 乗り換えの入口 |
| R1 日常ログ | 入力画面、コールサイン情報カード、Hamlib 連動、WSJT-X 連携、JCC / DXCC 判定、検索 | 毎日使ってもらう |
| R2 POTA / SOTA | 運用テンプレート、公園・サミット番号、複数公園の同時運用、公園ごとの出力、セルフスポット | 新しい利用者層 |
| R3 コンテスト | 規約エンジン（国内: JARL 電子ログ、海外: Cabrillo）、重複・パーシャルチェック、得点、バンドマップ、CW キーヤー、fldigi / MMTTY 連携 | 中核の差別化 |
| R4 発展 | クラスタ、アワード（DXCC / JCC / WAJA）、QSL 印刷・LoTW、マルチオペ、SO2R | 機能の拡充 |

R1 と R3 の順序は未決事項 Q1 で決める。各段階の完了条件は「実際に使える物が動き、テストが緑であること」とし、文書の更新は完了条件にしない。

## 7. 先に確認すべきリスク

- データの利用条件: JCC / JCG リスト、DXCC データ（cty.dat など）、POTA 公園・SOTA サミットのリストの再配布・更新の可否
- macOS 対応: 署名・公証、Lazarus の Cocoa 対応の成熟度を R0 の段階で実機確認する
- 規約定義の運用: 国内外コンテストの規約を誰が書き、毎年の改定にどう追従するか
- 電波型式の対応表: FT8 / RTTY などのモードと、免許の電波型式との対応をデータとして保守する
