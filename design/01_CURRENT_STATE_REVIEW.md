# `Lazarus/` 現状レビュー

対象: master `be47c0d`（2026-10-17 時点）
検証環境: Linux x64 コンテナ、Free Pascal 3.2.2。Windows / macOS / LCL GUI / 実機は未検証。

## 1. 結論

設計の方向性（層の分離、ポートと依存性注入、値オブジェクト、壊れにくいジャーナル）は良好。
ただし master はコンパイルできず、ロギングアプリの中核機能（重複チェック、得点、規約、出力、QSO の修正・削除）は未実装。
現状は「QSO を安全に保存する土台」と「無線・音声まわりの技術試作」の段階にある。

## 4. 性能面（実測）

`382e13f` に `cwstring` を追加した状態で計測。

| 項目 | 結果 |
|---|---|
| メモリ上リポジトリへ 10 万件登録 | 326 ms |
| ID による検索 1 万回 | 22 ms |
| 直近 50 件の取得 1000 回 | 7 ms |
| ジャーナル追記（fsync 込み）200 件 | p95 1 ms、最大 2 ms |
| RTTY 参照実装 | 35,842 bit/s（45.45 baud の約 790 倍速） |

懸念点:

1. 起動時、UI スレッド上でジャーナル全体を同期的に読み直す（`TMainForm.Create` から）。1 件につき 2 回のオブジェクト生成がある。
2. ジャーナル途中の 1 件の破損でアプリが起動できなくなる。救出・隔離の手段がない。末尾の切り詰めはバックアップなしで行われる。
3. 索引が ID のみ。重複チェックには（コールサイン、バンド、モード）の索引が必要。

## 5. オブジェクト指向の観点

良い点:

- domain → application → infrastructure → presentation の依存方向が守られている
- ポートとコンストラクタ注入、nil チェック、値オブジェクト（`TCallsign.TryCreate` など）、結果型によるエラー返却
- Presenter と描画専用 View の分離、上限付きキュー、ワーカー例外の隔離

改善点:

- `TQso` は不変のデータなのにクラスで、`Clone` が多い。`FindById` は呼び出し側が解放するオブジェクトを返し、`GetRecent` はレコードを返すなど、所有権の扱いが統一されていない
- `TMainForm` が同じ実体をオブジェクト参照とインターフェース参照の両方で保持しており、二重解放を招きやすい
- モードを `Ord(TEmissionMode)` で保存しており、列挙の途中に値を追加すると既存データの意味が変わる
- エラー箇所を文字列（`'callsign'`）で受け渡している
- `TSystemClock` がローカル時刻から UTC に変換しており、夏時間の切り替え時に曖昧になる
- QSO 1 件の非同期保存にインターフェースが 5 つあり、機能に対して抽象化が重い
- テストは 1,500 行の手書きランナー 1 本で、FPCUnit を使っていない

## 6. 開発プロセス

- 文書が約 1,800 行あり、コード約 5,800 行に対して比重が大きい。実装より先に「完了」と書かれる傾向がある
